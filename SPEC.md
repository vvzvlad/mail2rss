# mail2rss — спецификация

**Статус:** черновик v2, готов к реализации
**Дата:** 2026-07-15
**Изменение против v1:** конфиг фидов упразднён. URL сам является конфигом (§4).

---

## 1. Задача

В Fastmail приходят рассылки; правила ящика раскладывают их по папкам. Нужно получать **один Atom-фид на папку**, читать в **Miniflux**, ничего не меняя в самом ящике.

### 1.1 Что считается успехом

1. Подписался в Miniflux на `https://rss.example.com/f/tech/M9f3ac21b/{mac}/atom.xml` — вижу письма из папки `RSS/Tech` как записи.
2. Письма в ящике **не меняются**: ни `\Seen`, ни перемещений, ни удалений. Токен Fastmail физически read-only.
3. Картинки в письме видны в Miniflux (включая инлайновые `cid:`).
4. Трекинг-пиксели вырезаны; отправитель не узнаёт ни факт открытия, ни IP читателя.
5. Фид не ломает Miniflux: валидный XML, разумный размер, стабильные id (записи не «всплывают» повторно как непрочитанные).
6. **Новая папка = ничего не настраивать.** Взял `mailboxId` из `mail2rss folders`, посчитал ссылку в браузере на странице сервиса (или через `mail2rss url`). Ни конфига, ни рестарта, ни деплоя.
7. **Хранить нечего.** Удалил том с данными — ничего не потерялось: все URL выводятся заново из секрета.

### 1.2 Что в scope НЕ входит (v1)

- Отправка/модификация почты, любые write-операции в JMAP.
- Веб-UI сверх страницы выдачи ссылок; поиск, теги, собственная читалка.
- Мульти-юзер, регистрация, биллинг.
- Push (JMAP EventSource) — см. §12.
- Отзыв **одного** фида без смены всех остальных URL — принципиально невозможен без состояния, см. §4.7.

## 2. Ключевые факты, на которых стоит дизайн

Собраны исследованием (RFC 8620/8621, доки и живые эндпоинты Fastmail, исходники Miniflux, разбор ~10 существующих проектов). Каждый пункт — ограничение, из которого выведено решение.

| # | Факт | Следствие для дизайна |
|---|---|---|
| F1 | Fastmail: API-токен типа **JMAP**, скоупы «Read-only access» + «Email» → строго чтение почты. На плане Basic токенов нет. | Read-only **по конструкции**, а не по дисциплине кода. Мутация ящика невозможна физически. |
| F2 | JMAP `Email.id` **иммутабелен**: не меняется при перемещении между папками и смене флагов (RFC 8620 §1.2, RFC 8621 §2). IMAP UID при `MOVE` — пересоздаётся (RFC 6851 §3.1). | Берём **JMAP, не IMAP**. Главный технический аргумент. |
| F3 | Папка = `Mailbox`; вложенность только через `parentId`, **свойства «полный путь» в JMAP нет**. `Mailbox.id` иммутабелен. | Адресуем папку по `mailboxId`, а не по пути (§4.2). Пути нужны только человеку, на странице выдачи ссылок. |
| F4 | JMAP-`Id` по RFC 8620 §1.2 состоит только из символов URL-safe base64 (`A–Z a–z 0–9 - _`), ≤255 октетов. | `mailboxId` кладётся в путь URL **как есть** — ни экранирования, ни percent-encoding. |
| F5 | JMAP отдаёт **уже декодированные** `subject`/`from` (RFC 2047 отработан сервером). | Класс багов «кириллица в теме превратилась в мусор» (LetterFeed #6) не существует. |
| F6 | Blob'ы (картинки/вложения) отдаются с **другого хоста** `fastmailusercontent.com` и требуют `Authorization: Bearer`. | Вставить URL Fastmail в фид **нельзя**. Обязателен свой медиа-прокси (§8.1). |
| F7 | Push: `/jmap/event/` существует, но **в доках Fastmail не описан**, а с API-токеном исторически отвечал 401 (JMAP-Samples #7). | База — **polling**. Push не проектируем даже опционально в v1. |
| F8 | Miniflux **не скачает фид больше 15 MiB** (`HTTP_CLIENT_MAX_BODY_SIZE`). LetterFeed #24: фид разросся до 23 МБ, читалки отвалились. | Жёсткие лимиты размера — требование, а не оптимизация (§7.4). |
| F9 | Miniflux вырезает `script`/`style`/`noscript` **вместе с содержимым**, выкидывает `style`/`class`/`bgcolor`, режет 1×1-пиксели, чистит `utm_*`, форсит `rel="noopener noreferrer"`. | На CSS письма рассчитывать бессмысленно — Miniflux его выбросит. Режем стили сами, «красоту» не спасаем. |
| F10 | Miniflux резолвит **относительные** URL в контенте против URL фида. | В фид уходят **только абсолютные https-URL**. Иначе `src="/pixel.gif"` превратится в URL на нашем домене под capability-путём. |
| F11 | Miniflux хеширует запись по `atom:id`; **смена id = запись всплывает как новая и непрочитанная**. | `atom:id` детерминирован, глобален и неизменен навсегда (§7.2). |
| F12 | Miniflux умеет HTTP Basic, но NetNewsWire его принципиально не поддерживает (issue открыт с 2018), Feedly — тоже. | Аутентификация — **подпись в path** (capability URL). Работает везде, не запирает нас в Miniflux. |
| F13 | Miniflux по умолчанию **не** проксирует https-картинки (`MEDIA_PROXY_MODE=http-only`); при `MEDIA_PROXY_MODE=all` — проксирует все, со своего сервера. | Приватность remote-картинок закрывается **настройкой Miniflux**, а не нашим кодом (§8.2). Требование к развёртыванию. |
| F14 | Miniflux **хранит записи у себя** в БД после первого фетча. | Statelessness дёшева: удалённое в Fastmail письмо исчезнет из фида, но у читалки останется. |
| F15 | `bleach` (Python) — **EOL**, «no future releases including security fixes». | Санитайзер — **nh3** (биндинг к Rust-ammonia, активен). |
| F16 | Готового решения «фид = папка моего ящика» не существует; `cid:`-картинки не поддерживает **ни один** из ~10 разобранных проектов. | Пишем сами. Заимствуем идеи (детект пикселей — colporteur, защита медиа-прокси — email2rss). |
| F17 | Письма содержат control-символы, ломающие XML (LetterFeed #26: «All strings must be XML compatible»). | Обязательная чистка `\x00-\x08\x0b\x0c\x0e-\x1f` **на выходе**. |

## 3. Архитектурное решение

**Stateless-прокси без конфигурации.** Источник правды — Fastmail. Своей базы нет. Списка фидов нет. **Фид описан самим URL**, а подпись в URL доказывает, что этот URL выпустил владелец секрета.

```
Miniflux ──GET /f/{slug}/{mailboxId}/{mac}/atom.xml──► mail2rss ──JMAP──► Fastmail
   │                                                      │  1) проверить mac
   │                                                      │  2) Email/query(inMailbox=mailboxId)
   │                                                      │     + Email/get  (2 call'а, 1 HTTP)
   │                                                      ▼
   │                                              transform + sanitize
   │◄──────────────── Atom 1.0 ───────────────────────────┘
   │
   └──GET /f/…/{mac}/m/{blobId}/{sig}/{name}──► mail2rss ──Bearer──► fastmailusercontent.com
                                                  (стриминг картинки, LRU-кэш на диске)

Человек ──GET /──► статический калькулятор: MAC считается в браузере
                   (id папок и OPML — из CLI: mail2rss folders / opml)
```

### 3.1 Почему так

- **Нет БД писем → нет целого класса задач**: инкрементальный sync, `state`-токены, `cannotCalculateChanges` с полным ресинком, дедупликация, retention, миграции схемы. Самый баговый кусок любого IMAP/JMAP-клиента просто не пишется.
- **Нет конфига фидов → нет ещё одного класса задач**: автообнаружение, коллизии ключей, переопределения, детект переименований, рестарты при изменении конфига. Всё это было в v1 и вычеркнуто.
- **Нет расхождения состояний.** Переложил письмо в другую папку — оно само переехало в другой фид. Удалил — исчезло.
- F14 гасит главный минус statelessness: Miniflux уже сохранил запись у себя.
- Цена: каждый запрос фида = поход в JMAP. Гасится кэшем (§6.3); Miniflux по умолчанию опрашивает фид раз в 60 минут.

### 3.2 Роль SQLite

**SQLite — одноразовый кэш, не источник правды.** Файл можно удалить в любой момент: сервис продолжит работать, только первый запрос будет медленнее. Хранит:

- `media_cache` — тела blob'ов (иммутабельны по RFC 8620 §6.2, инвалидация не нужна), LRU по размеру.
- `render_cache` — отрендеренный HTML записи, ключ = `email_id` (иммутабелен, F2) + `render_version`.
- `feed_cache` — последнее успешно отрендеренное тело фида + ETag (нужно для stale-отдачи, §6.4).
- `mailbox_tree` — дерево папок (для `children=1`, заголовка фида и CLI-команд `folders`/`feeds`/`opml`).

Никаких таблиц «письма», «фиды», «токены», «прочитанность».

## 4. Как задаются папки: URL и есть конфиг

### 4.1 Форма URL

```
/f/{slug}/{mailboxId}/{mac}/atom.xml[?limit=50&children=1]
   └─┬──┘ └────┬────┘ └─┬─┘
     │         │        └── HMAC: единственное, что проверяется
     │         └── что запрашиваем в JMAP (иммутабельно, F3)
     └── косметика для человека; при проверке ИГНОРИРУЕТСЯ
```

Три решения, каждое со своим обоснованием:

**1. Подпись покрывает `mailboxId`, а не имя папки.** Если бы MAC считался от пути, переименование папки убивало бы URL — а это отвалившаяся подписка в Miniflux. `Mailbox.id` иммутабелен (F3), поэтому переименовал папку → **URL продолжает работать**.

**2. Имя папки всё равно есть в URL — как неподписанный slug.** Нужно человеку: видеть в Miniflux и в логах, какой фид какой. Сервер slug **не проверяет, не сравнивает и ни на что не опирается** — чистая косметика. Переименовал папку → URL продолжает работать со старым slug'ом; `<title>` фида всё равно берётся из живого `Mailbox.name`, так что Miniflux покажет актуальное имя. Канонизирующих редиректов нет: лишний код ради косметики.

**3. Настройки фида — в query, и они входят в MAC.** Конфига нет, жить им негде. Обязательно внутри подписи: иначе любой держатель ссылки поставит `limit=100000` и превратит фид в способ выжирать наш JMAP-бюджет.

Почему `mailboxId` можно класть в путь без экранирования: JMAP-`Id` состоит только из `A–Z a–z 0–9 - _` (F4). Ни percent-encoding, ни разбора путей, ни NFC-нормализации, ни экранирования `/` внутри имени папки — ничего этого больше нет.

### 4.2 Вывод ключей и подписи

```
K_feed  = HKDF-SHA256(MAIL2RSS_SECRET, info="mail2rss/feed-mac/v1")
K_media = HKDF-SHA256(MAIL2RSS_SECRET, info="mail2rss/media-sig/v1")   # domain separation

mac = base32( HMAC-SHA256(K_feed,  mailboxId ‖ 0x00 ‖ canon(params) ‖ 0x00 ‖ epoch) )[:26]   # 128 бит
sig = base32( HMAC-SHA256(K_media, mac       ‖ 0x00 ‖ blobId) )[:26]
```

- `canon(params)` — канонизация: только известные параметры, дефолты выброшены, ключи отсортированы, `k=v` через `&`. Неизвестные параметры при проверке **отбрасываются и в MAC не входят** (иначе `?x=1` работал бы как cache-buster).
- Ключи для фидов и для медиа разведены через HKDF-`info`: один HMAC-ключ не должен обслуживать две разные цели.
- `epoch` — см. §4.7.
- Компрометация одного URL **не даёт** вывести другие (прообраз HMAC).
- Секрет в env один: `MAIL2RSS_SECRET` (плюс `FASTMAIL_API_TOKEN`). Ротация всех URL = смена секрета.

Плата: `MAIL2RSS_SECRET` — единая точка отказа. Он и так лежит рядом с токеном Fastmail, который даёт доступ ко **всей** почте, так что поверхность атаки это не расширяет.

### 4.3 Параметры фида (v1)

| Параметр | Дефолт | Потолок | Смысл |
|---|---|---|---|
| `limit` | 20 | 100, форсится сервером независимо от подписи | Записей в фиде |
| `children` | `0` | — | `1` — включать письма из подпапок: фильтр `{"operator":"OR","conditions":[{"inMailbox":"<родитель>"},{"inMailbox":"<ребёнок>"},…]}`. Список детей берётся из дерева папок в момент запроса, **в подпись не входит** → новая подпапка подхватывается сама. |

Расширяемость даром: любой будущий фид «по отправителю» или «по поиску» — это просто новый MAC'нутый параметр (`?from=…`), а не новая сущность в конфиге (§12).

### 4.4 Страница выдачи ссылок

`GET /` → статическая страница-**калькулятор**. Весь расчёт выполняется **в браузере** (WebCrypto: HKDF-SHA256 → HMAC-SHA256, побайтово идентично §4.2): пользователь вводит `mailboxId` (берётся из `mail2rss folders`, §4.5), секрет и опционально имя папки (косметический slug), `limit`, `children`, `epoch` — и получает готовый URL с кнопкой «скопировать».

**На сервер не отправляется ничего.** POST-маршрута не существует, форма никуда не сабмитится. Сервер не отдаёт никаких данных ящика — ни дерева папок, ни OPML по HTTP; его единственное участие — отдать статическую страницу с вшитым `BASE_URL`. Дерево папок и OPML доступны только через CLI (§4.5: `mail2rss folders`, `mail2rss opml`).

**Вопрос об «оракуле» исчезает полностью:** сервер в вычислении не участвует, ему нечего сравнивать и нечего подтверждать. Раньше секрет гейтил листинг папок — теперь листинга по HTTP просто нет. Соответственно отпадают и POST-only, и rate limit, и constant-time сравнение: ограничивать и сравнивать нечего.

Требования (гигиена страницы):

1. **Секрет валидируется на старте сервиса.** `MAIL2RSS_SECRET` обязан быть машинно-сгенерированным (`make gen-secret`, 128 бит, base32); не проходит проверку формата/энтропии → сервис **не поднимается**. Больше секрет нигде не перепроверяется — страница его никуда не отправляет.
2. CSP только inline, никаких внешних ресурсов (скриптов/шрифтов/аналитики); `autocomplete="off"`, `<meta name="referrer" content="no-referrer">`, `X-Robots-Tag: noindex`.
3. Секрет не логируется нигде и не попадает в трейсбеки — на сервере его и не бывает: он не покидает браузер.
4. WebCrypto доступен только в secure context: страница работает по HTTPS (или на localhost). При загрузке выполняется self-test с эталонным вектором; если `crypto.subtle` недоступен или вектор не сошёлся — страница явно сообщает, что калькулятор не работает.

### 4.5 CLI (то же самое офлайн)

Всё считается без обращения к сервису; Fastmail нужен только там, где перечисляются папки.

- `mail2rss gen-secret` — сгенерировать `MAIL2RSS_SECRET`.
- `mail2rss folders` — дерево папок с `mailboxId`.
- `mail2rss url --mailbox M9f3ac21b [--limit 50] [--children]` — готовый URL, **без обращения к Fastmail**.
- `mail2rss opml > feeds.opml` — OPML со всеми папками.
- `mail2rss check` — токен Fastmail жив, сессия резолвится, `BASE_URL` выглядит как https.

### 4.6 Таблица отказов (почему именно так)

| Событие | Что происходит с URL фида |
|---|---|
| Переименовали папку | ✅ Работает как ни в чём не бывало. В URL остаётся старый slug — косметика, всем плевать; заголовок фида берётся из живого `Mailbox.name`. |
| Перенесли папку к другому родителю | ✅ Работает: `mailboxId` не менялся. |
| Добавили новую папку | ✅ Фид доступен сразу, без рестарта. Ссылка: взять id из `mail2rss folders` и посчитать URL на `/` (или `mail2rss url`). |
| Появилась новая подпапка внутри папки с `children=1` | ✅ Подхватывается сама (список детей в подпись не входит). |
| Удалили и создали папку заново с тем же именем | ❌ Новый `mailboxId` → URL мёртв (`410`). Это семантически другая папка. Восстановление: взять новый id из `mail2rss folders` и посчитать ссылку на `/` (или `mail2rss url`). |
| Переехали на другой аккаунт Fastmail / восстановили ящик из бэкапа | ❌ Все `mailboxId` новые → все URL мертвы. Восстановление: перезалить OPML в Miniflux. |
| Переставили сервис, сохранив секрет | ✅ Все URL те же. Данные (`/data`) можно не переносить. |
| Переименовали папку, и она выпала из `MAIL2RSS_ALLOWED_FOLDERS` | ❌ `404` до правки паттерна или имени (§4.8). |
| Утёк URL одного фида | ⚠️ См. §4.7. |

Два «❌» из stateless-дизайна — осознанная цена за полное отсутствие состояния. Оба редки, оба чинятся одной страницей. Третий существует только при включённом allowlist (§4.8) и чинится правкой паттерна или имени.

### 4.7 Отзыв: единственное, чего stateless не умеет

**Отозвать один фид, не тронув остальные, без состояния невозможно** — отзыв по определению есть состояние. Варианты, от простого к сложному:

1. **Дефолт:** утёк URL → сменить `MAIL2RSS_SECRET` → **все** URL сменились → перезалить OPML в Miniflux (одна операция). Для личного сервиса — нормальная цена.
2. **Escape-hatch без файла конфига:** env `MAIL2RSS_EPOCH="M9f3ac21b:2,M77bb01c:5"` — счётчик, входящий в MAC (§4.2). Бампнул для одной папки → сменился URL только у неё. Формально это состояние, но оно живёт в env рядом с секретом, а не в БД, и в 99% случаев пусто.
3. Полноценный revocation-list в БД — **не делаем**: возвращает всё, что вычеркнули в §3.1.

Смягчающее обстоятельство: URL утекает только через Miniflux (наш же сервер) и логи; сторонним сайтам он не отдаётся благодаря `Referer`-политике (§5.2).

### 4.8 Жёсткий серверный allowlist папок

Ограничение blast radius утёкшего URL и даже утёкшего `MAIL2RSS_SECRET`: даже валидный MAC для папки вне списка не отдаёт **ничего**. Дополняет epoch (§4.7): epoch отзывает конкретный уже выданный URL, allowlist заранее ограничивает, какие папки вообще могут быть отданы.

- env `MAIL2RSS_ALLOWED_FOLDERS` — comma-separated fnmatch-глобы по полному пути папки («Parent/Child»; литеральный `/` в имени экранируется как `\/`). Пусто → ограничения нет, поведение байт-в-байт текущее. Непустое значение, распарсившееся в ноль паттернов (например `" , ,"`), → сервис **не стартует** (fail loudly, как у `MAIL2RSS_EPOCH`): оператор, который считает, что ограничение действует, не должен молча получить «разрешено всё».
- Матчинг — `fnmatch.fnmatchcase` (детерминированный, регистрозависимый). `*` в fnmatch **пересекает** `/`: `Newsletters/*` покрывает всё поддерево; саму папку `Newsletters` добавляют отдельным паттерном.
- Семантика отказа: папка не подходит под паттерны → **голый `404`, байт-в-байт как при неверном MAC**, тихо. НЕ фид-с-объяснением (§6.4), не `403` — ничего не подтверждаем. Гейт срабатывает **до кэша** (кэш переживает рестарты: папка, заблокированная новым паттерном после рестарта, не должна дослуживать кэшированное тело до истечения `cache_ttl`) и **до медиа-прокси** (медиа-URL живут вечно в HTML записей Miniflux). Дети в `children=1` фильтруются по тем же паттернам, чтобы запрещённая подпапка не утекала через агрегатный фид разрешённого родителя.
- Fail closed: allowlist включён, а дерева папок нет вообще (первый старт во время недоступности Fastmail) → `503`, никогда не fail open. Удалённая папка (`unknown`) сохраняет обычную семантику маршрута (фид-с-объяснением и т.п.) — allowlist её не касается.
- Переименование папки так, что она выпала из паттерна, **немедленно** убивает её фид — осознанное следствие «жёсткости»; лечится возвратом имени или правкой паттерна (§4.6).
- Таймлиз: `404` blocked-папки отличим от `404` плохого MAC разве что по таймингу обработки; это требует валидного MAC — принято.

## 5. HTTP API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/f/{slug}/{mailboxId}/{mac}/atom.xml` | Atom-фид папки |
| GET | `/f/{slug}/{mailboxId}/{mac}/e/{emailId}.html` | Permalink письма (полный текст, без обрезки) |
| GET | `/f/{slug}/{mailboxId}/{mac}/m/{blobId}/{sig}/{name}` | Медиа-прокси (картинки, вложения) |
| GET | `/` | Калькулятор ссылок: MAC считается в браузере, секрет на сервер не отправляется |
| GET | `/health` | Живость + статус последнего похода в JMAP (дёргается healthcheck'ом из compose) |
| GET | `/robots.txt` | `User-agent: *` / `Disallow: /` |
| GET | всё прочее | `404` |

### 5.1 Проверка запроса

1. Отбросить неизвестные query-параметры, канонизировать известные.
2. Пересчитать `mac` от `mailboxId` + `canon(params)` + `epoch`; сравнить **constant-time** (`hmac.compare_digest`). Не совпало → `404` (не `401`/`403`: не подтверждаем существование папки).
3. Slug **полностью игнорируется**: не проверяется, не сравнивается, редиректов на «канонический» вид нет.
4. `limit` форсится к потолку сервером независимо от того, что подписано.
5. Тот же `mac` авторизует permalink и медиа этого фида. Permalink открывается внешним браузером и отдельного логина не требует.
6. Permalink дополнительно проверяет, что письмо действительно лежит **в этой** папке (или в её подпапке при `children=1`) — по `mailboxIds` из ответа `Email/get`. Иначе ссылка одного фида читала бы письма из любой папки ящика.
7. После MAC — жёсткий allowlist папок (§4.8), на всех трёх capability-маршрутах (фид, permalink, медиа): папка вне `MAIL2RSS_ALLOWED_FOLDERS` → голый `404`, байт-в-байт как при неверном MAC. При пустом env шаг полностью отсутствует.

Slug **никогда** не попадает в HTML/XML без экранирования и не влияет ни на маршрутизацию, ни на кэш-ключ.

### 5.2 Обязательная обвязка capability-URL

Из W3C TAG «Good Practices for Capability URLs» — риск утечки высок, поэтому это требования:

1. Только HTTPS + HSTS.
2. `X-Robots-Tag: noindex, nofollow, noarchive` на фиде, permalink, медиа и `/` + `Disallow: /` в robots.txt.
3. На permalink-странице: `<meta name="referrer" content="no-referrer">`, на всех исходящих ссылках `rel="noopener noreferrer nofollow"`. Иначе клик по ссылке из письма отдаст наш capability-URL стороннему сайту в `Referer`.
4. `Cache-Control: private` — никогда `public`.
5. **`mac` не попадает в логи**: пишем `mailboxId` и первые 6 символов хеша `mac`. Секрет на сервер вообще не приходит (§4.4).
6. Rate limit на `mac` (§6.5).
7. Никаких сторонних скриптов/шрифтов/аналитики.

## 6. Поток обработки запроса фида

### 6.1 Дерево папок

`Mailbox/get` с `ids: null` (папок мало — тянем все разом) → дерево по `parentId`. Нужно для трёх вещей: канонический slug и `<title>` фида (= `Mailbox.name`), список детей при `children=1`, CLI-команды `folders`/`feeds`/`opml`.

- Кэш — 1 час, обновление по таймеру → новая папка видна без рестарта. Принудительный сброс при `notFound` от JMAP.
- Сбой обновления → **работаем на последнем удачном дереве** (разовый сбой Fastmail не должен обнулять все фиды).
- `mailboxId` не существует (папку удалили) → фид-с-объяснением (§6.4), permalink → `410 Gone`. Не `404`: подпись валидна, клиент не виноват, папки просто больше нет.
- Заголовок фида берётся из `Mailbox.name`; переименовать фид локально всегда можно в самом Miniflux — поэтому поля `title` в URL нет.

### 6.2 Запрос писем — один HTTP-запрос, два method call'а

```json
{
  "using": ["urn:ietf:params:jmap:core", "urn:ietf:params:jmap:mail"],
  "methodCalls": [
    ["Email/query", {
      "accountId": "u1234abcd",
      "filter": { "inMailbox": "<mailboxId>" },
      "sort": [ { "property": "receivedAt", "isAscending": false } ],
      "limit": 20,
      "calculateTotal": false
    }, "q"],
    ["Email/get", {
      "accountId": "u1234abcd",
      "#ids": { "resultOf": "q", "name": "Email/query", "path": "/ids" },
      "properties": [
        "id", "blobId", "mailboxIds", "subject", "from", "sender",
        "receivedAt", "sentAt", "messageId", "preview", "hasAttachment",
        "htmlBody", "textBody", "bodyValues", "attachments",
        "header:List-Unsubscribe:asURLs", "header:List-Id:asText"
      ],
      "bodyProperties": ["partId","blobId","size","name","type","charset","disposition","cid"],
      "fetchHTMLBodyValues": true,
      "fetchTextBodyValues": true,
      "maxBodyValueBytes": 1000000
    }, "g"]
  ]
}
```

Лимиты Fastmail (`maxCallsInRequest: 50`, `maxObjectsInGet: 4096`, `maxConcurrentRequests: 10`) не задевают: 2 вызова, ≤100 объектов.

`bodyValues[partId].isTruncated == true` → тело урезано сервером; для фида этого достаточно (мы всё равно обрезаем, §7.4), для permalink — дотягиваем часть целиком по `blobId`.

### 6.3 Кэш и минимальный интервал

- `cache_ttl` (дефолт 600 с, env): если с прошлого похода в JMAP прошло меньше — отдаём закэшированное тело. Miniflux по умолчанию опрашивает раз в 60 мин, так что реальная нагрузка на Fastmail — единицы запросов в час.
- Ключ кэша = `mailboxId` + `canon(params)`.
- Публичных rate-limit'ов на чтение Fastmail не публикует → самоограничиваемся: не чаще 1 запроса в `cache_ttl` на фид, экспоненциальный backoff на `429`/`5xx`.

### 6.4 Поведение при ошибках

Разделяем **временный сбой** и **постоянную поломку** — читалка на них реагирует по-разному.

**Временный сбой (JMAP недоступен, 5xx, таймаут):**

1. Есть `feed_cache` (даже протухший) → отдаём его, `200`, заголовок `X-Upstream-Status: stale`, WARN в лог.
2. Кэша нет → `503` + `Retry-After: 300`. Miniflux пометит фид ошибкой и повторит — это правильное поведение для временного сбоя.
3. Никогда не отдаём **пустой** фид при ошибке апстрима: пустой валидный фид Miniflux воспримет как «записей нет», а не как сбой. Это классический тихий баг.

**Постоянная поломка (папка удалена, `mailboxId` не существует):** отдаём **валидный фид с одной записью-объяснением** («папка удалена из Fastmail; ссылка больше не работает»), а не голый `410`. Идея взята из `create_error_feed()` в pyrogram-bridge: голый 4xx превращается в красный счётчик ошибок, который пользователь месяцами игнорирует, а запись в ленте он реально прочитает.

Требование к такой записи: **стабильный `atom:id`** (`UUIDv5(ns, "error:" + mailboxId)`) — иначе она будет всплывать непрочитанной при каждом опросе фида. Именно на этом и ломаются наивные реализации error-фидов.

### 6.5 Rate limit

На `mac`: 60 запросов/час (норма Miniflux — 1/час, запас на ручные обновления) → `429` + `Retry-After`. Отдельно: WARN, если один `mac` опрашивают с >3 разных ASN — вероятная утечка capability-URL.

### 6.6 HTTP-кэширование

- `ETag` = strong, `sha256` тела фида. `Last-Modified` = `receivedAt` самой свежей записи.
- `If-None-Match` / `If-Modified-Since` → `304` без тела (Miniflux шлёт оба).
- `Cache-Control: private, max-age=300`; gzip обязателен.

## 7. Рендер фида

### 7.1 Формат

**Atom 1.0, единственный формат.** Причины: однозначная спека escaping'а (RFC 4287 §4.1.3.3), `atom:id` и `updated` — **обязательные** элементы (формат сам заставляет делать правильно), нормальное разделение `published`/`updated`. RSS тянет за собой `content:encoded` vs `description` и ловушку `isPermaLink`.

Контент — в `<content type="html">`, **экранированный** (не CDATA с сырым XML). Внутри не должно быть `<html>`, `<head>`, `<body>`, `<!DOCTYPE>`, `<base>`, XML-деклараций: содержимое обязано быть валидным как внутренность `<div>`.

**Сериализатор — свой, на `lxml.etree`, а не `feedgen`.** Соседний pyrogram-bridge использует feedgen, но в RSS-режиме и с `type='CDATA'`; для Atom нам нужно ровно противоположное — экранированный `type="html"`, и документация feedgen этого поведения не фиксирует. Плюс своё: полный контроль над вычисткой control-символов (F17), детерминированная побайтовая сериализация (от неё зависит стабильность ETag) и отсутствие чужих причуд (в feedgen у соседа имя автора пришлось запихивать в поле `email`). Это ~60 строк, которые целиком закрываются golden-тестами и прогоном через feedvalidator (§11).

### 7.2 Идентичность записи (критично)

```
atom:id = urn:uuid:<UUIDv5(ns = NAMESPACE_MAIL2RSS, name = message_id)>
```

- `message_id` — первый элемент JMAP-свойства `messageId` (заголовок `Message-ID`, RFC 5322): глобально уникален по определению и не меняется никогда.
- **Не привязываем id к папке.** Иначе пересоздание папки (новый `mailboxId`) сделало бы все записи «новыми» в Miniflux. Одинаковый `atom:id` в двух разных фидах безвреден: Miniflux хеширует записи в пределах фида.
- **Сам Message-ID в фид не выводим**: у ряда ESP он содержит идентификатор подписчика — публикация светила бы наш subscriber-token.
- Нет `messageId` (кривой отправитель) → fallback `UUIDv5(ns, sha256(receivedAt ‖ from ‖ subject ‖ preview))`.
- **JMAP `Email.id` в качестве `atom:id` НЕ используем**: он иммутабелен в 99.9% случаев, но при слиянии тредов сервер вправе пересоздать письмо с новым id (RFC 8621) → запись всплыла бы как непрочитанная. `Email.id` — только ключ кэша и часть permalink-URL.
- **Схема id версионируется и никогда не применяется задним числом** (F11).

### 7.3 Поля записи

| Поле | Источник | Правила |
|---|---|---|
| `title` | `subject` | plain text, без разметки, до 200 символов. Пустая тема → детерминированный fallback `«(без темы) — {from} — {дата}»`. |
| `link rel="alternate"` | наш permalink | `{base_url}/f/{slug}/{mailboxId}/{mac}/e/{emailId}.html`. **Уникален для каждой записи** — Miniflux использует URL как fallback-ключ дедупликации. |
| `author/name`, `author/email` | `from[0]` | display-name и адрес. |
| `published` | **`receivedAt`**, не `sentAt` | `receivedAt` монотонен и не подделывается отправителем. `Date` (`sentAt`) регулярно врёт (будущее/далёкое прошлое), а читалки игнорируют записи с датой из будущего. |
| `updated` | `receivedAt` | Меняется только при реальном ре-рендере (смена `render_version`). |
| `category` | `header:List-Id`, домен `from` | Miniflux их показывает. |
| `content type="html"` | §7.5 | Обрезка по §7.4. |

Фид-уровень: `<title>` = `Mailbox.name`, `<id>` = `urn:uuid:UUIDv5(ns, mailboxId)`, `<updated>` = max(`published`), `<link rel="self">` = **канонический** URL (с актуальным slug).

### 7.4 Размеры (F8)

- ≤ `limit` записей (дефолт 20, потолок 100).
- Контент записи > 200 КБ → **обрезка по границе блочного элемента** (`p`, `div`, `table`, `h*`, `ul`, `figure`), никогда не по сырым байтам (иначе битый XML), + хвост `<p><a href="{permalink}">Читать письмо целиком →</a></p>`.
- Суммарный фид > 1 МБ → **уменьшаем число записей**, а не режем контент сильнее.
- Абсолютный потолок 15 MiB (Miniflux не скачает) — не приближаемся на порядок.

### 7.5 Пайплайн контента

Выбор части: `text/html` (последняя альтернатива в `multipart/alternative`) → `text/plain` → «нет содержимого».

Порядок строгий; **санитайзер — последний, как security gate**, а не первый:

1. **Parse** (`lxml.html`, с учётом `charset` из JMAP).
2. **Base**: прочитать `<base href>`, запомнить, **удалить тег**.
3. **Вырезать вместе с содержимым**: `script`, `style`, `noscript`, `iframe`, `object`, `embed`, `form`, `input`, `button`, `select`, `option`, `textarea`, `svg`, `head`, `title`; все HTML-комментарии (в т.ч. MSO conditional); все namespaced-элементы (`v:*`, `o:*`, `w:*`, `x:*` — иначе fallback-текст из VML-кнопки выведется вторым экземпляром рядом с настоящей).
4. **Абсолютизация URL** против `<base>`. Нерезолвимый относительный URL → удалить атрибут. **В фид не уходит ни одного относительного URL** (F10).
5. **`cid:` → медиа-прокси** (§8.1). Неразрешённый `cid:` → `<img>` удалить.
6. **Трекинг-пиксели**: удалить `<img>` при `width`/`height` ≤ 1 (в атрибутах **или** в inline-style), нулевой площади, `display:none`, известных путях (`/open`, `/o/`, `/track/`, `/pixel`). Miniflux режет только 1×1 по атрибутам — на него не перекладываем.
7. **Tracking-параметры** в ссылках: вычистить `utm_*`, `mc_eid`, `fbclid`, `gclid`, `yclid`, `_openstat`.
8. **Click-редиректы НЕ разворачиваем.** Резолв редиректора — это HTTP-запрос, который ESP **засчитает как клик**: мы бы «кликали» за пользователя по всем ссылкам письма. Ссылки `unsubscribe`/`preferences`/`optout` не трогаем **никогда** — там одноразовые токены, известны случаи ложных отписок от сканеров ссылок.
9. **Семантизация вёрстки**: развернуть layout-таблицы (без `<th>`/`<caption>`), снять `<font>`, `<center>`; кнопку-таблицу с одной ссылкой → `<p><a>`.
10. **Стили и цвета — вырезать полностью** (`style`, `class`, `bgcolor`, `background`, `align`, `valign`, `cellpadding`, `cellspacing`, `border`). Причины: (а) Miniflux их всё равно выбросит (F9); (б) частично применённый CSS ломает читаемость сильнее, чем его отсутствие: `color: black` без `background: white` = чёрное на чёрном в dark-режиме читалки.
11. Всем `<a>` — `rel="noopener noreferrer nofollow"`.
12. `List-Unsubscribe` → явная ссылка в футере записи.
13. **Санитайзер `nh3`** (F15) — финальный проход:

```python
# Security gate: runs last, after all transformations.
TAGS = {"p","br","hr","h1","h2","h3","h4","h5","h6","strong","b","em","i","u","s",
        "code","pre","blockquote","q","cite","ul","ol","li","dl","dt","dd",
        "a","img","figure","figcaption","picture","source",
        "table","thead","tbody","tfoot","tr","th","td","caption",
        "small","sub","sup","abbr","time","span","div"}
ATTRS = {"a": {"href","title"},
         "img": {"src","alt","title","width","height"},
         "td": {"colspan","rowspan"}, "th": {"colspan","rowspan"},
         "time": {"datetime"}, "abbr": {"title"}}
# clean_content_tags, not just "absent from TAGS": otherwise <style> contents leak as text.
CLEAN_CONTENT = {"script","style","noscript","iframe","object","embed",
                 "form","input","button","select","option","textarea","svg","title","head"}

nh3.clean(html,
          tags=TAGS, attributes=ATTRS, clean_content_tags=CLEAN_CONTENT,
          strip_comments=True,                       # kills MSO conditional comments
          link_rel="noopener noreferrer nofollow",
          url_schemes={"http", "https", "mailto"},   # no data:, cid:, javascript:
          url_relative="deny")                       # belt and braces for F10
```

14. **Чистка XML-несовместимых символов — из ВСЕХ строк, а не только из контента** (F17). Касается `title`, `author`, `category`, `content` — всего, что уезжает в XML. Полный набор запрещённых XML 1.0 символов:
    - управляющие C0: `[\x00-\x08\x0B\x0C\x0E-\x1F]`;
    - одиночные суррогаты `[\uD800-\uDFFF]`;
    - **non-characters `￾` и `￿`** — их легко упустить (в наивном регэкспе «контрол-символы + суррогаты» их нет), а lxml бросает на них ту же `ValueError`. Достижимы при битой декодировке / неверной обработке UTF-16 BOM.

    Это не перестраховка, а **проверенный исполнением** отказ: lxml (и построенный на нём feedgen) бросает `ValueError: All strings must be XML compatible`, причём **CDATA от этого не спасает** — исключение возникает и там. Итог: **один такой символ в одном письме роняет весь фид** (500 на каждый опрос, пока письмо не уедет из окна). В pyrogram-bridge такой чистки нет вообще — в Telegram эти символы практически не встречаются, поэтому баг ни разу не выстрелил. В почте они рутина: битые кодировки, `\x0c`, криво декодированный quoted-printable.

    **Belt-and-braces:** дополнительно к вычистке сериализация Atom (`build_atom`) оборачивается в fail-safe — на `ValueError` при `etree.tostring` фид не отдаёт 500, а до-чищает/деградирует. Вычистка — первая линия, обёртка — гарантия, что никакой будущий несовместимый символ не сможет уронить фид целиком.

15. Обрезка по §7.4.

### 7.5.1 Ошибка рендера одного письма не должна ронять фид

Два правила, оба выведены из чужих граблей:

- **Изоляция:** санитайз и рендер выполняются **по одному письму**; исключение на одном письме не отравляет остальные (паттерн из pyrogram-bridge, §14.1).
- **Деградация, а не тишина:** если письмо не отрендерилось, в фид уходит **урезанная запись** (тема + отправитель + дата + ссылка на permalink + пометка «не удалось отрендерить тело») с тем же стабильным `atom:id`. **Молча выбрасывать письмо запрещено.** В pyrogram-bridge такая ошибка логируется и делает `continue` — запись просто исчезает из фида, и при стабильном guid это не видно вообще никак: пользователь не узнает, что письмо было.

### 7.6 text/plain fallback

Не оборачивать в `<pre>` (ломает перенос на мобильном). Конвертер: учесть `format=flowed`/`DelSp` (RFC 3676, иначе рваные строки по 72 символа) → экранировать → пустая строка = новый `<p>`, одиночный перевод = `<br>` → цитаты `> ` в `<blockquote>` → linkify URL и email.

Ни html, ни text → запись с заголовком, ссылкой на permalink, пометкой «письмо без текстового содержимого» и списком вложений.

## 8. Медиа

### 8.1 Инлайновые `cid:`-картинки (то, чего нет ни у кого — F16)

В JMAP inline-часть лежит в `attachments[]` с полями `cid` (угловые скобки сняты сервером), `blobId`, `type`, `name`, `disposition: "inline"`.

1. Построить map `cid → blobId`.
2. `src="cid:XXX"` → `{base_url}/f/{slug}/{mailboxId}/{mac}/m/{blobId}/{sig}/{name}`.
3. `sig = HMAC(K_media, mac ‖ 0x00 ‖ blobId)` (§4.2). Подпись обязательна: без неё эндпоинт превращается в перебираемый по `blobId` прокси ко **всем** blob'ам аккаунта, включая письма из папок, к которым этот фид отношения не имеет.
4. Подпись **бессрочная**: Miniflux сохраняет HTML записи навсегда, протухающая подпись = битые картинки в старых записях.
5. **Отдача — самое опасное место всего сервиса.** Стрим из `downloadUrl` Fastmail с нашим Bearer, заголовки:
   - `Content-Type` — **только из декларации JMAP-части и только если он в allowlist** (`image/png|jpeg|gif|webp|avif`). Тип **не сниффим** (`python-magic` и подобное — запрещено). `image/svg+xml` запрещён явно: SVG — это вектор XSS.
   - `X-Content-Type-Options: nosniff` — **обязателен**. Именно он делает задекларированный нами тип авторитетным: даже если внутри blob'а лежит HTML, браузер не исполнит его как HTML, получив `Content-Type: image/png` + `nosniff`.
   - `Content-Security-Policy: sandbox; default-src 'none'` — эшелон защиты на случай ошибки в allowlist.
   - `Content-Disposition: inline` — только для типов из allowlist; всё прочее — `attachment` (§8.1 п. 7).
   - `Cache-Control: private, immutable, max-age=31536000` (blob'ы иммутабельны, RFC 8620 §6.2), `Content-Length`.

   **Модель угроз здесь принципиально жёстче, чем у соседей.** В pyrogram-bridge Content-Type определяется **сниффингом байтов**, отдаётся `inline`, а `nosniff` в проекте отсутствует вообще (§14.2). Там это узкая тропинка. У нас **атакующий выбирает байты вложения простым письмом на ваш адрес**: SVG или HTML, отданные `inline` с нашего origin, — это stored XSS **на том самом домене, в URL'ах которого лежат токены фидов**. Отсюда правило: тип задаём мы, не файл; сниффинга нет; `nosniff` есть всегда.
6. LRU-кэш blob'ов на диске (§3.2): без него каждый фетч Miniflux'ом бил бы в Fastmail.
7. Лимиты: ≤5 МБ на картинку, таймаут 10 с. Не-картиночные вложения — ссылкой в футере записи с `Content-Disposition: attachment`, не инлайном.

SSRF-риска нет: мы ходим не по URL из письма, а **только** по `downloadUrl` из JMAP-сессии с подставленным `blobId` — хост зафиксирован.

### 8.2 Remote-картинки отправителя

**Оставляем как есть.** Приватность закрывается на стороне Miniflux:

> **Требование к развёртыванию:** в Miniflux выставить `MEDIA_PROXY_MODE=all` (по умолчанию `http-only` — https-картинки **не** проксируются, и IP читателя утекает отправителю).

С этой настройкой Miniflux скачивает картинки со своего сервера → отправитель видит IP сервера Miniflux, а не читателя, и не получает подтверждения открытия в момент чтения.

**Принятый риск:** факт скачивания сервером Miniflux всё же происходит (один раз, при первом фетче). Полное решение (скачивать все картинки при приёме, не оставляя в фиде ни одного внешнего хоста) требует ingest-архитектуры и в v1 сознательно не делается. Трекинг-пиксели мы вырезаем сами (§7.5 п. 6), так что наружу идут только «настоящие» картинки.

## 9. Permalink письма

`GET /f/{slug}/{mailboxId}/{mac}/e/{emailId}.html` → `Email/get` по id → тот же пайплайн §7.5, **без обрезки** → минимальная HTML-страница.

- Нужен, потому что (а) `link` записи обязан быть уникальным и рабочим, (б) обрезанные письма надо где-то дочитать.
- Проверка принадлежности письма папке — §5.1 п. 6.
- Страница: `<meta name="referrer" content="no-referrer">`, `X-Robots-Tag: noindex`, никаких внешних ресурсов кроме картинок письма, минимальный свой CSS (читаемая колонка, light/dark через `prefers-color-scheme`).
- Письмо удалено или уехало из папки → `410 Gone`.

### 10.2 Конфигурация — только ENV, конфиг-файла нет

Это не компромисс, а прямое следствие §4: фиды описаны URL'ами, описывать в файле нечего.

```python
# src/settings.py
class Settings(BaseSettings):
    # Credentials: no defaults. Missing in env -> fail at startup with a clear message.
    fastmail_api_token: str
    mail2rss_secret: str        # 128-bit, base32; validated at startup (§4.4 p.1)

    # Own service address: no default either — it depends on the deployment.
    base_url: str               # e.g. https://rss.example.com

    # Public third-party API: a default is allowed here.
    jmap_session_url: str = "https://api.fastmail.com/jmap/session"

    # Non-secret tuning: defaults are fine.
    cache_ttl: int = 600
    max_limit: int = 100
    mailbox_tree_ttl: int = 3600
    mail2rss_epoch: str = ""    # "M9f3ac21b:2,..." — per-folder revocation (§4.7)
    mail2rss_allowed_folders: str = ""  # fnmatch globs over folder paths — hard allowlist (§4.8)
    log_level: str = "INFO"
    cache_db_path: str = "data/cache.db"   # state always under data/

    model_config = SettingsConfigDict(env_file=".env", extra="ignore")


settings = load_settings_or_exit(Settings)
```

Жёстко:

- `FASTMAIL_API_TOKEN`, `MAIL2RSS_SECRET`, `BASE_URL` — **без дефолтов**. Нет в env → падаем на старте с именем недостающей переменной (не с pydantic-трейсбэком).
- `BASE_URL` — адрес **своего** сервиса, поэтому дефолта не имеет принципиально: `http://localhost:8000` по умолчанию маскировал бы незаданную конфигурацию, и в фид уехали бы битые ссылки на localhost.
- `JMAP_SESSION_URL` — чужой публичный API, дефолт допустим.
- Никаких кред в коде, в тестах и в `docker-compose.yml` (там плейсхолдеры). `.env.example` коммитим полным, `.env` — нет.
- Дополнительно к соглашениям: **`MAIL2RSS_SECRET` проверяется на формат и энтропию при старте** (§4.4 п. 1) — слабый секрет не должен подниматься даже с корректным env.

## 11. Тестирование (DoD)

Тесты пишутся сразу, не «потом»: в CI `build` зависит от `test`. `tests/`, `pytest.ini` с `pythonpath = .`, общие фикстуры в `conftest.py`, каждому тесту — свежая БД через `tempfile`. HTTP к Fastmail **мокается через `respx`**, реальная сеть не дёргается ни в одном тесте. В `conftest.py` — `TZ=UTC` + `time.tzset()`, иначе golden-тесты дат недетерминированы (грабли из pyrogram-bridge, §14.1).

Отдельный инвариант-тест: **в репозитории ровно один `ALLOWED_TAGS`** — санитайзер не должен размножиться в две конфигурации, из которых одна окажется дырявой.

1. **Корпус писем-фикстур** (сохранённые JSON-ответы `Email/get`): HTML с таблицами и MSO-условками; `cid:`-картинки; text/plain с `format=flowed`; без темы; без `Message-ID`; с control-символами; 5 МБ HTML; кириллическая тема.
2. **Golden-тесты**: рендер фикстур → сравнение с эталонным Atom XML.
3. **Валидация**: фид проходит XML-схему Atom и feedvalidator без ошибок.
4. **Инварианты** (property tests): в контенте нет относительных URL, нет `<script>`/`<style>`/`style=`/`cid:`/`data:`, нет XML-несовместимых символов, нет `image/svg+xml`; размер фида ≤ лимитов; `atom:id` стабилен между прогонами.
4a. **Регрессы на чужие грабли** (каждый — против конкретного бага из §14.2):
   - письмо с `\x00`/`\x0c`/одиночным суррогатом **в теме и в теле** → фид валиден и содержит **все** записи (а не 500 на весь фид);
   - письмо, на котором рендер падает → в фиде **деградированная запись** с тем же `atom:id`, а не пропажа;
   - вложение с `Content-Type: image/svg+xml` → **не отдаётся**; вложение, где задекларирован `image/png`, а внутри HTML → отдаётся с `Content-Type: image/png` + `X-Content-Type-Options: nosniff` (тип **не сниффится** из байтов);
   - все даты в фиде — timezone-aware, ни одной из будущего, ни одной, меняющейся между двумя прогонами.
5. **Подпись и URL** (§4):
   - `mac` детерминирован: два запуска с одним секретом → один URL;
   - подделка `mailboxId` при валидном `mac` от другой папки → `404`;
   - подмена `?limit=100000` без пересчёта `mac` → `404`; с валидным `mac` → сервер всё равно форсит потолок;
   - неизвестный query-параметр не влияет ни на подпись, ни на кэш-ключ;
   - устаревший slug → `301` на канонический, тело то же;
   - slug с XSS-нагрузкой (`<script>`) не попадает в HTML/XML неэкранированным;
   - бамп `MAIL2RSS_EPOCH` для одной папки меняет только её URL;
   - медиа-`sig`, выпущенный для другого фида, → `404`;
   - permalink письма из другой папки → `410`/`404`, а не контент.
6. **Страница выдачи ссылок**: `GET /` отдаёт статический калькулятор без каких-либо данных ящика и с гигиеническими заголовками (CSP, noindex, no-referrer, no-store); `POST /` → `405` (маршрута нет); self-test-константы в шаблоне сходятся с Python-реализацией MAC (паритет JS ↔ Python до байта).
7. **Деградация**: JMAP отвечает 500 → фид отдаёт stale-кэш с `X-Upstream-Status: stale`, не пустой фид и не 500. Удалённый `mailboxId` → `410`.
8. **Конфигурация**: пустое окружение → падение на старте с перечислением недостающих переменных (`FASTMAIL_API_TOKEN`, `MAIL2RSS_SECRET`, `BASE_URL`), без pydantic-трейсбэка. Слабый `MAIL2RSS_SECRET` → отказ подниматься. Удаление `data/cache.db` → сервис работает (проверка «кэш действительно одноразовый»).
9. **Интеграционный smoke**: живой Miniflux в docker-compose подписывается на фид, показывает записи, картинки грузятся.

## 12. Открытые вопросы и отложенное

| Тема | Решение v1 | Почему |
|---|---|---|
| Отзыв одного фида | Смена глобального секрета либо `MAIL2RSS_EPOCH` | Отзыв = состояние; полноценный revocation-list возвращает всё, что вычеркнули (§4.7). |
| Push (JMAP EventSource) | Нет | Не документирован Fastmail'ом, исторически 401 с API-токеном (F7). При stateless-архитектуре бесполезен: фид рендерится по запросу читалки. |
| Ingest в БД | Нет | Осознанный выбор. Триггеры к пересмотру: хранить письма дольше, чем они живут в почте; полностью убрать внешние хосты из фида. |
| Фиды по отправителю / поиску | Нет, но путь открыт | Достаточно нового MAC'нутого query-параметра (`?from=…` → `FilterCondition`), новых сущностей не появляется (§4.3). |
| Разворачивание click-редиректов | Нет | ESP засчитает наш резолв как клик (§7.5 п. 8). |
| Мульти-аккаунт Fastmail | Нет | Одна учётка, `primaryAccounts["urn:ietf:params:jmap:mail"]`. |
| RFC 5005 (paged feeds) | Нет | Поддержка у читалок практически нулевая. |

## 14. Переиспользование из pyrogram-bridge

`~/Data/Projects/pyrogram-bridge` — структурно тот же класс задачи (внешний API → парсинг → санитайз → фид + подписанный медиа-прокси + одноразовый кэш). Прошёл несколько рефакторингов и стабильно работает в проде, **но эталоном не является**: ниже разобрано, что берём как есть, что чиним при переносе и чего не повторяем. Всё «как есть» перед копированием читаем глазами — «работает в проде» ≠ «корректно», особенно там, где баг тихий.

### 14.1 Берём как есть (паттерн проверен и нам подходит)

| Оттуда | Что даёт |
|---|---|
| `sanitizer.py` — контракт модуля | **Fail-closed**: любое исключение санитайзера → `html.escape(raw)`, но никогда не сырой проброс. Один-единственный `ALLOWED_TAGS` на весь репозиторий (и тест, который это запирает). Единое имя лог-события + `log_context` для грепа. Warning, если санитайз занял >50 мс. Всё это переносим, заменив `bleach` на `nh3`. |
| Санитайз **по одному письму, внутри рабочего потока** | Кривое письмо экранируется изолированно и **не отравляет весь фид**. Структурные склейки делаются после санитайза, чтобы их не съело. |
| Весь CPU-тяжёлый рендер — в **одном** `asyncio.to_thread` | Не дёргаем пул на каждую мелочь; event loop не блокируется. |
| `tg_throttle.py` → `jmap_rpc_bounded()` | Гейт **снаруже**, таймаут **внутри**: ожидание в очереди не должно съедать бюджет таймаута самого запроса. Готовый класс багов, который иначе выводишь заново. |
| Pure-ASGI `RequestLoggingMiddleware` | Написан именно потому, что `BaseHTTPMiddleware` буферизует тело и ломает стриминг/фоновые задачи/отмену. Нам это критично: медиа-прокси стримит (§8.1). |
| Негативный кэш с экспоненциальным backoff + LRU-кап; дедуп «в полёте» через `asyncio.Future` + **detached** задача | Отвалившийся клиент не отменяет уже идущую закачку и не подвешивает остальных ждущих. Прямо ложится на прокси blob'ов. |
| `FileResponse` + заранее снятый `stat_result` | Range/If-Range/206/416/ETag/Last-Modified достаются бесплатно — для отдачи закэшированных картинок. |
| SQLite: `PRAGMA journal_mode=WAL` + `busy_timeout`, все функции синхронные с суффиксом `_sync` и вызовом через `asyncio.to_thread`, bulk-upsert через `executemany` | Готовая, обкатанная форма работы с кэшем. |
| Конверт дискового кэша: `{version, timestamp, jitter}`, атомарная запись через `os.replace`, **jitter TTL решается в момент записи** | Иначе на границе TTL кэш «мигает» между hit и miss. |
| `conftest.py`: `TZ=UTC` + `time.tzset()` | Golden-тесты дат становятся детерминированными. Обязательно (§11). |
| Стиль лога: `event_name: k v, k v`, snake_case, английский | Грепается. Перенимаем. |

### 14.2 Копируем, но чиним (там баг)

| Место | Что не так | Как у нас |
|---|---|---|
| **Нигде нет вычистки control-символов** перед сериализацией (🔴 подтверждено исполнением) | lxml/feedgen бросают `ValueError: All strings must be XML compatible`; **CDATA не спасает**. Один такой символ → **500 на весь фид** при каждом опросе. Не стреляло только потому, что в Telegram таких символов почти нет. | Чистка всех строк, а не только контента (§7.5 п. 14). Фикстура с control-символами — обязательный тест (§11). |
| **Медиа: Content-Type сниффится (`python-magic`), отдаётся `inline`, `nosniff` в проекте нет вообще** (🔴) | На Telegram — узкая тропинка. У нас байты вложения выбирает **отправитель письма** → stored XSS на домене, где в URL лежат токены фидов. | Тип — только задекларированный и только из allowlist, без сниффинга; `nosniff` + CSP sandbox обязательны (§8.1 п. 5). |
| Ошибка рендера поста → `logger` + `continue` | Запись **молча исчезает** из фида; при стабильном guid это невидимо. | Деградированная запись вместо тишины (§7.5.1). |
| Проверка токена: `token != Config["token"]` | Не constant-time. | Только `hmac.compare_digest` (§5.1). |
| `logger.error(f"invalid_token_error: token {token}, expected {Config['token']}")` | **Ожидаемый секрет пишется в лог.** Настоящая утечка. | Ни секрет, ни `mac` в логи не попадают никогда (§5.2 п. 5). |
| Подпись медиа: HMAC-**SHA-1**, обрезанный до **8 hex = 32 бита**, без срока и без скоупа | 32 бита — это защита от случайного любопытства, а не capability. | HMAC-SHA-256, 128 бит, привязка к `mac` конкретного фида (§4.2, §8.1). |
| Ключ подписи медиа хранится в файле `data/media_digest.key`, автогенерится при первом запуске | Снёс volume → **все медиа-URL, уже разосланные в Miniflux, мертвы**, и понять почему невозможно. | Ключ **выводится** из `MAIL2RSS_SECRET` через HKDF. Файла нет, `data/` остаётся действительно одноразовым (§3.2, §4.2). |
| Дата письма отсутствует → `datetime.now()` | Недетерминированно; запись «прыгает» и может уехать в будущее. | `published` = `receivedAt` из JMAP, он всегда есть; фолбэк на «сейчас» запрещён (§7.3). |
| Фиды без `ETag`/`Last-Modified`/`Cache-Control`/`304` | Каждый опрос читалки — полная перегенерация. | ETag/304 обязательны (§6.6). |
| Схема SQLite мигрируется через `ALTER TABLE` с проглатыванием `duplicate column name` | Для одноразового кэша это лишняя сложность. | Кэш **дропается и создаётся заново** при несовпадении версии схемы. Проще и честнее (§3.2). |
| Тесты **не гоняются в CI** (workflow сразу билдит образ) | Расходится с каноническими соглашениями. | `build` зависит от `test` (§10.5). |
| Dockerfile: root, без `.dockerignore` | — | non-root, `.dockerignore` отсекает `data/`, `tests/`, `.env` (§10.4). |

### 14.3 Не повторяем

- **Плоская раскладка в корне и `Config = get_settings()` на уровне импорта.** Из-за этого тесты вынуждены подменять `sys.modules['config']`. У нас — канонические `src/` + `pydantic-settings` + `load_settings_or_exit` (§10.1–10.2), тесты задают ENV, а не хирургию над импортами.
- **`api_server.py` на 1500 строк**, где перемешаны роутинг, закачка медиа, подметание кэша и определение MIME. Режем по зонам ответственности с первого дня (§10.1).
- **`bleach`** — EOL, без security-фиксов (F15). Только `nh3`. И allowlist у нас другой: письма требуют `table`/`tr`/`td`/`blockquote`/`h1-h6`, которых в Telegram не было, а `cid:` не было вовсе.
- **`feedgen`** — см. §7.1.
- **Байпас проверки токена для loopback-запросов** — граблю с `TRUSTED_PROXIES` за обратным прокси не тащим: у нас единственный способ доступа — подпись в URL.
- **TTL кэша в 8 часов.** У соседа это осознанный размен против Telegram-овского FLOOD_WAIT. У JMAP такого давления нет, а фид, отстающий на 8 часов, — это баг, а не фича. У нас `cache_ttl` = 10 минут (§6.3).
- **Наивные (timezone-naive) datetime.** JMAP отдаёт aware RFC3339 (`receivedAt`) — остаёмся aware сквозь весь пайплайн. У соседа naive-даты просачиваются в снапшоты без оффсета, из-за чего смена `TZ` контейнера сдвигает все даты, а `TZ=UTC` в тестах — не гигиена, а костыль, удерживающий это от разъезжания.
- **Блокирующие FS-вызовы на горячем async-пути** (`os.path.exists`/`getsize` на каждый запрос медиа) — при том что SQLite и magic там аккуратно вынесены в `to_thread`. Непоследовательность; у нас весь I/O либо async, либо в `to_thread`.

### 14.4 Что осознанно перенимаем из его культуры

Русскоязычная спека в репозитории с журналом адверсариального ревью, на которую потом ссылаются комментарии в коде («см. §7.5 п. 6») — это самая ценная привычка соседнего проекта. Этот файл — она и есть.
